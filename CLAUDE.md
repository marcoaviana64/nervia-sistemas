# nervia-sistemas — notas do projeto

Nome do conjunto: **Plataforma Nervia** (site + Área do Cliente + apps + backend). Documentação para o Marco, com diagramas: "Plataforma Nervia — Documentação" (https://claude.ai/code/artifact/c9432c68-f6c1-43f5-84da-f23853a624e1). Ao mudar serviços, segredos ou estrutura, atualizar também esse documento.

Repositório `marcoaviana64/nervia-sistemas`, com três partes:
- o **site da Nervia** (`site/index.html`);
- a **Área do Cliente** (`site/cliente/`): login único; cada cliente vê os apps liberados para ele, e o app abre num iframe dentro do site, sem sair da página;
- os **apps** que a Nervia vende (`site/apps/<nome>/`).

O primeiro app é o **Buscador de NF** (`site/apps/notas/`): busca NF-e (SEFAZ) e NFS-e (ADN nacional) emitidas contra os CNPJs dos clientes, com o A1 de cada empresa, de hora em hora.

Backend: Supabase (projeto `nervia-sistemas`, org Nervia, plano Pro, região São Paulo). Site: Cloudflare Workers com arquivos estáticos (`wrangler.jsonc`), o mesmo serviço da Linum. Domínio previsto: nervia.com.br.

## Estrutura
- `supabase/migrations/`
  - `..._nervia_base.sql` — comum a todos os sistemas Nervia do projeto: `perfis` (um login por pessoa; `admin` = equipe Nervia), `eh_admin()`, trigger que cria o perfil; `apps` (cadastro dos apps da Área do Cliente) e `app_acessos` (login×app), com RLS — cliente vê só app ativo e liberado.
  - `..._buscador_nf.sql` — tudo do Buscador com prefixo `nf_`: `nf_empresas`, `nf_acessos` (cliente×CNPJ), `nf_notas`, `nf_log`; RLS por CNPJ (`nf_pode_ver`); `nf_gravar_nota()`, `nf_salvar_certificado()` / `nf_ler_certificado()` (Vault), `nf_travar_empresa()`; bucket privado `nf-xml` com policy por CNPJ (pasta = CNPJ).
  - Próximos sistemas (ex.: atendimentos) entram no mesmo projeto com prefixo próprio, reaproveitando `perfis`.
- `supabase/functions/`
  - `sincronizar` — admin: `{cnpj, tipo:"nfe"|"nfse"}`; cron: header `x-cron-secret` → 202 e roda todas em `EdgeRuntime.waitUntil` (~120 s). Admin `{cnpj, acao:"recuperar_nfe"}` inicia a recuperação por consNSU (ver Requisitos); o cron continua a cada hora.
  - `ciencia` — evento 210210 nas NF-e selecionadas.
  - `certificado` — recebe .pfx+senha, valida com node-forge e guarda `{cert_pem,key_pem}` no Vault (senha e .pfx não são guardados).
  - `usuarios` — cria login (com apps, CNPJs e flag admin), edita nome e e-mail (`editar`: troca o e-mail no Auth já confirmado, sem e-mail de confirmação, e no perfil; recusa e-mail de outro login; auditoria `login_alterado` com antes/depois), exclui e troca senha (auth.admin). Usado pela Administração da Área do Cliente (Logins → "editar nome e e-mail").
  - `email` (admin: `situacao`, `teste`) e `email-auth` (gancho **Send Email** do Supabase Auth, assinatura Standard Webhooks conferida em `_shared/webhook.ts`): e-mail pelo **Microsoft 365** da Nervia (decisão do Marco em 22/10/2026, sem custo). `_shared/email.ts` pega token de aplicativo (client credentials) e faz `POST /users/{EMAIL_REMETENTE}/sendMail` no Graph (202 = aceito, cópia em Itens enviados). Remetente: caixa compartilhada **nao-responda@nervia.com.br** (sem licença; criada pelo Marco em 22/10/2026, com acesso do marco.viana). Permissão Mail.Send de APLICATIVO dada só pelo Exchange (RBAC for Applications, escopo = essa caixa), NÃO no Entra (lá valeria para todas as caixas). Segredos: `MS_TENANT_ID`, `MS_CLIENT_ID`, `MS_CLIENT_SECRET` (vence!), `EMAIL_REMETENTE`, `SEND_EMAIL_HOOK_SECRET`. Registro em `email_envios` (migração `..._email.sql`; sem o corpo; só admin lê; Administração → E-mails com teste). Link de senha nova = `{SUPABASE_URL}/auth/v1/verify?token=<token_hash>&type=<ação>&redirect_to=…`; auditoria `senha_link_enviado`. Na Área do Cliente, `CFG.ESQUECI_AUTOMATICO` (config.js) troca o pedido manual pelo link (`resetPasswordForEmail`) e a volta `#…type=recovery` abre "Criar senha nova" (`updateUser`). Passo a passo: IMPLANTACAO.md §8. Teste: `testes/email_test.ts`. Próximo: avisos dos apps pelo mesmo `_shared/email.ts`.
  - `_shared/` — `sefaz.ts`, `adn.ts`, `xml.ts`, `certificado.ts` (mTLS via `Deno.createHttpClient({cert,key})`, usado no ADN), `ponte.ts` (NF-e via ponte), `banco.ts` (interface `Banco` para testes), `http.ts` (`VERSAO` vai nas mensagens de erro).
- `ponte-sefaz/` — ponte Python/OpenSSL (só biblioteca padrão) no **Google Cloud Run** (southamerica-east1, deploy contínuo do GitHub pelo `ponte-sefaz/Dockerfile`). Recebe `{url,headers,body,cert_pem,key_pem}` com cabeçalho `x-ponte-segredo`, faz o POST com mTLS e devolve `{status,body}`. Só fala com hosts `*.nfe.fazenda.gov.br`; não guarda nem registra certificado. Segredos nas funções: `PONTE_URL`, `PONTE_SEGREDO` (com `PONTE_URL` definido a NF-e liga sozinha; sem ele, 409).

## Requisitos e limites conhecidos (conferidos na NT 2014.002 v1.40 e na documentação do ADN)
- NF-e (NFeDistribuicaoDFe):
  - Só ~90 dias: notas mais antigas não vêm (rejeição 632 fora da janela). A primeira carga de um cliente traz só os últimos ~90 dias.
  - **O emitente NÃO recebe as próprias NF-e.** As NF-e de VENDA do cliente nunca chegam pelo Buscador. Decisão do Marco (2026-10-14): **vendas não são captadas por enquanto** — visão "Vendas" do Painel escondida (`display:none`, código mantido), textos de site/PDF/demo/ajuda falam só de compras.
  - **O destinatário recebe só o RESUMO até manifestar** (ciência, confirmação ou desconhecimento). Toda NF-e de compra chega "só resumo"; o XML completo só vem depois da ciência (clique do admin, regra abaixo).
  - Um sistema por CNPJ (sequência única de NSU); 656 bloqueia o CNPJ inteiro 1h; repetir dentro da hora reinicia a contagem. Consulta por chave/NSU: máx. 20/h.
  - Lote de no máximo 50 documentos por resposta.
  - **distNSU não volta atrás**: se outro sistema já consumiu a sequência (ex.: Linum até NSU 419), pedir de NSU menor dá 656 ("SEFAZ informou ultNSU 419"). Usar o ultNSU da SEFAZ e recuperar as anteriores por **consNSU** (NSU específico; 137 = não achado/fora dos 90 dias, 589 = acima do máximo; limite 20/h, 656 bloqueia o CNPJ 1h). Botão "Recuperar NF-e anteriores" (migração `..._nf_recuperar_nsu.sql`, `recuperarAnteriores` em `sefaz.ts`): desce do `nfe_recuperar_nsu`, no máx. 15 consultas por rodada e 1 rodada a cada 61 min (`nfe_recuperar_em`), termina com 10 vazios seguidos ou NSU 0.
  - Numa 656 o Buscador NÃO avança o ultNSU (antes avançava para o ultNSU devolvido pela SEFAZ, o que podia pular notas em silêncio); só registra no histórico "[NSU nosso X; SEFAZ informou ultNSU Y, maxNSU Z]" (v8-nsu656).
- Manifestação do destinatário (NT 2020.001; conferir a versão vigente antes de mexer):
  - Ciência da Operação (210210): só até **10 dias** da autorização da NF-e (fora do prazo: rejeição 596). Não é conclusiva.
  - Conclusivas (Confirmação 210200, Desconhecimento 210220, Operação não realizada 210240): **90 dias** desde 01/06/2026 (v1.60, Ajuste SINIEF 14/2026; antes eram 180). Depois de uma conclusiva não cabe mais ciência (655).
  - Até 20 eventos por lote; 573 = duplicidade (já registrado, inclusive por outro sistema) — tratado como sucesso.
  - Se outro sistema já manifestou a nota, o XML completo vem para qualquer sistema do mesmo CNPJ.
  - Certificado: vale pela raiz (8 dígitos) — o A1 da matriz consulta filiais (a função `certificado` já aceita mesma raiz).

Edge Functions do Supabase NÃO abrem conexão nas portas 25 e 587 (doc "Edge Functions limits") → o SMTP do Microsoft 365 (587) não funciona de dentro das funções; usar Microsoft Graph (app no Entra, permissão Mail.Send restrita a uma caixa) ou um serviço com API HTTP (Resend/Brevo/SendGrid + DNS na Cloudflare). O SMTP próprio do Supabase Auth ("Esqueci minha senha") roda no servidor do Supabase e aceita host/porta/usuário/senha. Microsoft 365: SMTP AUTH com senha fica desligado por padrão no fim de dezembro de 2026 (MC786329; o admin pode religar; remoção final a anunciar no 2º semestre de 2027); precisa SMTP AUTH ligado na caixa e não funciona com "padrões de segurança"/MFA na conta; limite ~30 mensagens/min por caixa.
- RouterOS `/tool fetch` (doc oficial, conferida em 17/10/2026): POST com `http-method=post`, `http-header-field="h1:v,h2:v"`, `http-data` até 64 KB; HTTPS não confere o certificado por padrão (`check-certificate=no`; o tráfego é cifrado, mas sem validar o servidor — aceitável porque o token só grava medições daquele equipamento). A doc não cita SNI nem versão mínima: por isso o script começa com o teste `/tool fetch url="https://nervia.com.br/"` (Cloudflare exige SNI) antes de instalar em roteador v6. `flood-ping ... do={ $"avg-rtt" }` não está garantido na v6: fica em `on-error` (sem latência, status continua certo pelo `/ping`). Antes de instalar em cada roteador, LER o equipamento (rotas, gateways, failover) — regra da skill mikrotik-padrao-nervia.
- Escala: o cron roda ~120 s por hora para todas as empresas; com muitas empresas (estimativa: acima de ~15–20) nem todas cabem numa rodada. Rever antes de passar disso.
